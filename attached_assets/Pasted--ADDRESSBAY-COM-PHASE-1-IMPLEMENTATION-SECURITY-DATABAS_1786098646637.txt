# ADDRESSBAY.COM — PHASE 1 IMPLEMENTATION

## SECURITY + DATABASE FOUNDATION ONLY

We have completed the architecture audit of the existing India Companies Directory application.

The audit confirmed the following critical issues:

1. `requireAdmin` currently checks only whether the user is authenticated.
2. Any authenticated Replit/OIDC user can currently access `/api/admin/*`.
3. The current `companies` table is India-specific.
4. There is no proper `country_code`.
5. There is no global registration-number architecture.
6. Company search uses unindexed `ILIKE '%query%'`.
7. The application needs to eventually support millions of companies across India, Australia, UK and Singapore.
8. The existing large-file importer needs a separate later phase.
9. Existing India data must be preserved.

## IMPORTANT

This is PHASE 1 ONLY.

DO NOT implement the entire AddressBay transformation now.

DO NOT implement:

* XML streaming importer
* background import workers
* partner system
* Legal Filing India integration
* sitemap redesign
* SEO page engine
* PIN-code pages
* country pages
* UI redesign
* Google Ads
* analytics
* Australia/UK/Singapore importers

Those are later phases.

The objective of this phase is to establish a SAFE, BACKWARD-COMPATIBLE database and security foundation.

# STEP 2 — FIX ADMIN AUTHORIZATION FIRST

This is a live security issue.

Current behavior:

`requireAdmin` checks only:

`req.isAuthenticated()`

This is NOT sufficient.

Change the server-side middleware so that:

1. User must be authenticated.
2. User email must exist in the `admins` table.
3. Only then may the request access `/api/admin/*`.

The authorization decision must happen on the server.

Never rely on:

* frontend buttons
* hidden routes
* React state
* `isAdmin` UI flags

as the security mechanism.

Use the existing `storage.isAdmin()` or an equivalent database lookup.

# STEP 5 — GLOBAL COMPANY FOUNDATION

We need to transform the existing India-only company model into a global model without destroying current data.

Add a proper:

`country_code`

Initial supported values:

* `IN`
* `AU`
* `GB`
* `SG`

Do NOT immediately remove it.

# STEP 6 — GLOBAL REGISTRATION IDENTIFIER

The current `cin` field is India-specific.

Add:

`registration_number`

This will become the normalized global company registration identifier.

Examples:

India:
CIN

Australia:
ACN or appropriate primary registration identifier

United Kingdom:
Companies House company number

Singapore:
UEN

Do NOT assume every country's identifier is identical.

For this phase:

* preserve existing `cin`
* preserve all existing India records
* populate `registration_number` from existing CIN where appropriate
* do not delete CIN yet

Do not create country-specific detail tables unless the migration design requires them.

We will handle country-specific schemas in a later phase after reviewing actual datasets.

# STEP 11 — SAFE INDEXING

Review the current indexes before adding anything.

The future company database may contain millions of rows.

Create only indexes that are justified by actual queries.

At minimum evaluate indexes for:

* `country_code`
* `registration_number`
* `slug`
* `state`
* `city`
* `district`
* `status`
* `source`

For name search, evaluate PostgreSQL `pg_trgm`.

Do not blindly create indexes on every column.

Remember:

More indexes improve reads but increase storage and write/import cost.

The final index strategy must consider the future bulk-import workload.
